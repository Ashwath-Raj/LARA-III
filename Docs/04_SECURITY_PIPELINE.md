# Security Pipeline and Action Enforcement

## Purpose

This document specifies the enforcement path for every agent action. The permission defaults are defined in `09_AUTONOMY_POLICY_MATRIX.md`; the schemas and service boundaries are defined in `03_DATA_AND_CHUNKING.md`, `05_ARCHITECTURE.md` and `06_API_CONTRACT.md`.

**Models propose; trusted code authorizes and executes.** The language model is not the policy engine.

## Required action pipeline

Every tool call must pass through this sequence, including calls made by a persona, a browser workflow, a resumed background job or another tool.

1. **Normalize request:** parse the proposed operation into a registered tool name and typed arguments. Reject unknown tools and invalid arguments.
2. **Establish identity:** resolve user, requesting persona, active job, room context and provider destination from trusted application state. Do not accept self-asserted roles from model output.
3. **Resolve target and data labels:** identify target resource, source rooms, sensitivity labels, local/cloud destination and potential side effects.
4. **Evaluate policy:** apply deny rules first, then persona/tool/resource permissions and risk-tier rules from `09_AUTONOMY_POLICY_MATRIX.md`. Fail closed if policy evaluation fails.
5. **Validate preconditions:** check path/domain allowlists, file ownership/scope, argument bounds, timeouts, budgets and current task state.
6. **Decide approval:** if approval is required, create a pending approval bound to the normalized action arguments and stop before executing the action.
7. **Revalidate approval:** immediately before execution, verify that approval is current, unexpired, granted by the authorized user, unused, and bound to the identical action and target. Re-check policy in case permissions changed.
8. **Execute through a narrow adapter:** use the registered implementation, not an arbitrary shell string generated by the model.
9. **Verify outcome:** check an authoritative result or postcondition. Record `succeeded`, `failed` or `unverified`; do not equate an attempted click with success.
10. **Audit and checkpoint:** append a safe audit event, persist the result and advance the job only after its state has been recorded.

No alternate execution path may bypass this pipeline.

## Deterministic permission decision contract

All protected reads and writes use one policy interface; callers cannot ask the model to decide access or assert their own scope.

`evaluate_access(context: AccessContext) -> PolicyDecision`

`AccessContext` is built from trusted application state and contains: `principal_id`, `persona_id`, nullable `job_id`, `room_id`, `resource_id` (or a typed resource scope), `action_id`, `sensitivity_label`, `destination` (`local` or a configured provider/service ID), `risk_tier`, current `system_mode`, and any approval reference. For multi-resource operations, evaluate each resource and require all decisions to allow. Missing/unknown identity, room, sensitivity, destination, resource ownership or risk is a denial.

`PolicyDecision` contains `decision` (`allow`, `deny`, `requires_approval`), `policy_id`/version, a sanitized reason, decision time, and an effective scope/filter when applicable. Only trusted policy code can create the filter. Clients and models cannot widen it. `requires_approval` stops before the side effect; it is not an allow.

The policy evaluator applies hard denies first, then the defaults in `09_AUTONOMY_POLICY_MATRIX.md`, explicit user grants, task/job scope and destination constraints. The executor re-evaluates immediately before any side effect. For reads, authorization must precede returning content or metadata. Denials must not disclose whether a protected resource exists, its title, count, citation, or room label.

### Enforcement points

- **Graph:** authorize the requested node and its room before lookup results are exposed; authorize both endpoint nodes and the edge before returning an edge or neighborhood. Apply filters in the data query where possible and re-check each result before serialization.
- **Vector/RAG:** policy derives the Qdrant room/resource filter before search. Qdrant results are untrusted candidate IDs; fetch active records and text from SQLite and re-check authorization before ranking, snippet generation, citation construction or counts.
- **Model routing:** evaluate the task and each context item against the selected provider before prompt assembly, then re-check the assembled disclosure set immediately before send. Denial blocks that route; no silent provider fallback.
- **Tools:** validate typed tool arguments, build trusted context, evaluate policy, validate preconditions, enforce approval, and re-check policy/approval immediately before invoking the narrow adapter.
- **Cross-room bridges:** authorize the source and bridge grant, confirm destination, purpose, field allowlist, expiry and revocation, then expose only projected fields. A bridge never grants graph traversal into its source room or cloud use unless its separate policy permits it.

Missing room or sensitivity metadata is not inferred from the caller, model output, Qdrant payload or a display name. Treat such records as quarantined/unavailable until trusted metadata is repaired. Policy service failure, malformed context or an unknown action/risk is fail-closed.

## Risk tiers

| Tier | Meaning | Default handling |
|---|---|---|
| 0 — Read | Read permitted memory, files, webpages or authorized service data | Allowed only when persona, room, resource and provider scope permit it |
| 1 — Prepare | Draft text, plans, commands, code diffs or a pending submission | May run autonomously within approved scope; no external side effect |
| 2 — Reversible workspace write | Modify files in an approved workspace with checkpoint/diff and rollback path | Allowed only for explicitly granted workspace paths and registered operations; otherwise approval required |
| 3 — External/destructive | Send, submit, publish, delete important data, alter accounts, replace submitted work or make purchases | Fresh explicit approval for the exact action and target |
| 4 — Privileged system action | `sudo`, system-wide installation, security changes, permission changes or credential access | Separate elevated approval with complete impact preview; use a narrow privileged helper when possible |

Approval is necessary for some actions but is not sufficient to make an unsafe operation allowed. Deny rules remain in force. The model **never receives an unrestricted root shell** and must not generate commands that are blindly piped to a shell.

## Approval object

An approval must be specific and short-lived. Persist at least:

- unique approval ID and associated job
- registered action/tool name
- normalized target and arguments, with an argument hash
- human-readable preview and stated consequence
- requesting principal and approving user
- policy rule/version that required or allowed the action
- creation time, expiry, decision and execution status

Any change to the tool name, target, file, recipient, course, assignment, command or material argument invalidates the approval. Consuming an approval is atomic so two workers cannot execute it twice. Never reuse an approval across retries that could produce a new external side effect unless the adapter can prove the original action did not occur and policy explicitly allows safe retry.

For command approvals, show command, working directory, environment changes and affected paths. For Classroom, show course, assignment, exact attachment and operation. For cloud disclosure, show provider and categories of context to be sent.

## Data disclosure checks

Before constructing a cloud prompt, evaluate every retrieved context item against room policy, sensitivity and provider destination. Retrieve the minimum context needed for the task. Personal Vault, Health and credential/authentication artifacts remain local-only by default. Provider UI sessions, cookies and OAuth tokens are never model context.

A policy denial must not reveal restricted content through error text, counts, graph labels or citations. Return a generic denial plus an actionable next step.

## Untrusted content and prompt injection

Treat web pages, emails, files, screenshots, model output and tool output as untrusted data. Such content may contain apparent instructions, but it cannot modify system policy, expand room access, install tools, authorize external actions or change the identity of the requester.

Controls:

- Separate model-generated plans from tool execution.
- Validate schemas and enforce bounds in deterministic code.
- Keep provider cookies, authentication data and browser profiles isolated.
- Restrict browser navigation to configured origins where appropriate.
- Never follow instructions found in a webpage to reveal memory or secrets.
- Stop on unexpected login, consent, CAPTCHA, anti-automation, payment or permission-changing screens.

## Filesystem and terminal enforcement

- Default to an approved workspace and canonicalize paths before checking access.
- Reject path traversal and symlink escapes from approved directories.
- Prefer dedicated tools such as `read_file`, `list_workspace`, `apply_patch` and `run_tests` over general shell access.
- Before a write, save a diff/checkpoint and verify repository/worktree state.
- Destructive operations must enumerate affected targets and require approval.
- `sudo` is not available to the model as a generic tool. Any privileged action must use a reviewed, narrowly-scoped helper and a separate approval path.
- Git rollback does not undo emails, submissions, remote API calls, untracked files or system configuration changes.

## Failure rules

- Policy engine unavailable or uncertain: deny and stop.
- Approval expired or action arguments changed: require new approval.
- Verification inconclusive: set state to `unverified` or `verification_needed`.
- Browser state changed unexpectedly: pause rather than guess.
- Repeated identical failure: stop retrying and report the blocker.
- Global pause/kill switch activated: stop dispatching new actions and interrupt cancellable work. Record any currently in-flight external action as potentially uncertain.
- Room or sensitivity metadata missing/inconsistent, or SQLite authorization re-check unavailable: deny the read and do not expose snippets, graph labels, citations, counts or cloud prompt content. Qdrant availability never substitutes for the authoritative access check.
